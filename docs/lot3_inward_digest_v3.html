Corrections to the first digest

  • Stale returns do NOT skip signature and fraud. All 21 stale instruments ran signature (21/40 overall) and fraud (40/40 overall) before the date rule returned them. My v1 claim was wrong.
  • v1's "13 OCR date/payee low-confidence" tile was mislabelled and is removed.
  • The Tesseract header check was silently off in earlier runs (never pointed at the Windows install), so the earlier "40/40 type" used 2 signals, not 3. It is on in this run: 4 instruments (#3, #4, #5, #35) now disagree and go to human review as instrument_type_split; #35 is a real cheque that the model and the DD pass both read as a DD, which is the case the third signal exists to catch.
  • Fraud now runs for every instrument, including those that exit early to human review: 40 of 40 scored by the XGBoost + SHAP stand-in (synthetic training data, not real fraud detection).
  • The 90-day validity limit is kept deliberately: these are 2025 instruments, so none can read as STP. This run measures extraction quality, not STP rate.

What is real and what is stubbed

  • Real: live API, Temporal workflows, image OCR, MICR parsing, instrument-type vote, decision rules, DB writes.
  • Stubbed / not production: fraud scores come from a real XGBoost model with real SHAP values, but the model is a SYNTHETIC STAND-IN trained on rule-labelled data (plumbing proof, not real fraud detection; each result is labelled xgboost_synthetic_standin); OCR runs on the cloud fallback because no on-prem GOT-OCR2/vLLM is deployed in dev; CBS and NGCH are dev stubs; signatures are each cheque's own image enrolled as the specimen (proves plumbing, not authenticity); account numbers are synthetic.
  • Handwritten payee safeguard: each cheque payee is read twice (second read = zoomed Pay-line crop). If the two reads do not match letter-for-letter the name is withheld, both readings are shown, and the instrument goes to human review; it is never rescued past review. Live on 22 cheques: wrong payees shown 4 to 0. Cost: about half are withheld for review, several of which were actually right (the second read is noisy), and #22 (Post vs Port) is read the same way both times so it still passes. A better on-prem handwriting model is what reduces the review load.
  • Known limits: in-window MICR digit misreads need a branch MICR master or the NGCH presentment cross-check; #34 and #36 are the same physical cheque; two-line amount words (#28) cause a false mismatch.
  • Newest guards, now exercised on real images: an implausible DD date or a DD amount-read disagreement goes to human review (see #13 and #19 below).
