Corrections to the first digest

  • Stale returns do NOT skip signature and fraud. All 30 stale instruments ran signature (30/40 overall) and fraud (30/40 overall) before the date rule returned them. My v1 claim was wrong.
  • v1's "13 OCR date/payee low-confidence" tile was mislabelled and is removed.
  • The 90-day validity limit is kept deliberately: these are 2025 instruments, so none can read as STP. This run measures extraction quality, not STP rate.

What is real and what is stubbed

  • Real: live API, Temporal workflows, image OCR, MICR parsing, instrument-type vote, decision rules, DB writes.
  • Stubbed / not production: fraud score is the rule-based fallback (no trained XGBoost model exists); OCR runs on the cloud fallback because no on-prem GOT-OCR2/vLLM is deployed in dev; CBS and NGCH are dev stubs; signatures are each cheque's own image enrolled as the specimen (proves plumbing, not authenticity); account numbers are synthetic.
  • Known limits: handwritten cheque payees still have confident near-misses and wrong reads; in-window MICR digit misreads need a branch MICR master or the NGCH presentment cross-check; #34 and #36 are the same physical cheque; two-line amount words (#28) cause a false mismatch.
  • Newest guards, now exercised on real images: an implausible DD date or a DD amount-read disagreement goes to human review (see #13 and #19 below).
