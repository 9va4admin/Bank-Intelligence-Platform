Architecture

Two-Tier Vault Pattern

Every vault (except Cheque Leaf) uses the same architecture: Redis as the sub-millisecond hot cache during the IET decision window, YugabyteDB as the durable source of truth that survives Redis restarts without needing a CBS call.

Tier 1 — Hot (Redis)
Sub-millisecond lookup. Keyed by HMAC-SHA256 — raw account numbers never appear as Redis keys. No TTL on signature/account vaults — refreshed by VaultSyncWorkflow daily at 07:00. Cold restart: warm from YugabyteDB, no CBS call needed.
sig:{bank_id}:{hmac(bank_id:acct)}:{signatory_id}
Tier 2 — Durable (YugabyteDB)
Source of truth. Active-active across 2 DCs (RPO=0). Not queried during the 600ms IET decision window — only on Redis miss or cold-start warm. Audit trail of every sync event, CBS version, and model version.
cts.signature_embeddings
cts.account_signatories
cts.pps_vault_entries …
Vault miss policy (non-negotiable, Layer 1): Any miss — Redis error, key not found, or DB error — always routes to HUMAN_REVIEW. Never AUTO_RETURN.

Sync Mechanisms — Current State

All CTS vaults are synced via CBS API through VaultSyncWorkflow (Temporal, daily 07:00 + event-triggered). MSV uses file-drop exclusively.

VaultTriggerMethodScheduleCBS Connector Call
V1Signature SCHEDULED + EVENT CBS API Daily 07:00 + on-demand list_signature_specimens(bank_id)
V2PPS SCHEDULED + EVENT CBS API Daily 07:00 + on-demand list_positive_pay_records(bank_id)
V3Account SCHEDULED + EVENT CBS API Daily 07:00 + on-demand list_account_profiles(bank_id)
V4Cheque Leaf SCHEDULED CBS API Daily 07:00 only list_issued_leaves(bank_id)
V5Stop Payment SCHEDULED + EVENT CBS API Daily 07:00 + on customer instruction list_stop_payments(bank_id)
V6Signatory Registry BANK FILE DROP FILE FULL daily + DELTA intra-day — (file-drop only)
Event trigger: When CBS pushes a change event (account frozen, new PPS registered, stop payment raised), a Kafka message lands on cts.vault.sync.{bank_id}, which triggers VaultSyncWorkflow immediately rather than waiting for 07:00. Temporal's idempotent workflow IDs prevent concurrent runs for the same bank.

Vault Bulk Upload — Two Channels

Two upload channels exist for seeding and updating all CTS vault types. Both channels converge on VaultUploadProcessor, which handles hashing, encryption, DB writes, and Redis warm in a single pass.

Channel 1 — Manual UI: POST /v1/cts/vault/upload/{vault_type} — authenticated (bank_it_admin or ops_manager). Synchronous. File size limit: 20 MB. Returns batch summary immediately. Roles: LEAF_STATUS and PPS allow ops_manager; all other types require bank_it_admin.
Channel 2 — SFTP / File-Drop: Bank drops a CSV file to MinIO bucket astra-vault-drops/{bank_id}/{vault_type_lower}/{filename}.csv. MinIO event notification fires webhook → POST /v1/cts/vault/upload/file-drop → Temporal starts VaultFileDropWorkflow. Workflow ID includes SHA-256 of file bytes — duplicate MinIO events for the same file are silently de-duplicated. Processed files are archived to astra-vault-archive/{bank_id}/.
Both channels: changed_by is set to user:{user_id} (UI) or system:{feed_name} (file-drop). Every batch is written to cts.vault_upload_batches (bank_id scoped). upload_channel column records which path was used.

Temporal Workflow: VaultFileDropWorkflow

Workflow ID: cts-vault-drop-{bank_id}-{vault_type_lower}-{file_hash[:16]} — idempotent, same file never processed twice. Registered in CTS worker under cts-processing-{bank_id} task queue.

  1. 1
    fetch_drop_fileDownload CSV bytes from MinIO bucket astra-vault-drops. Verify SHA-256 against file_hash in the workflow input — mismatch aborts immediately. Returns raw CSV bytes.
  2. 2
    process_vault_csvInstantiates VaultUploadProcessor with bank-scoped vault instances (SignatureVault, PPSVault, ChequeLeafVault, AccountVault). Streams CSV rows. Per row: HMAC-SHA256 account number via shared.utils.pii_crypto.hash_account_number (bank-specific pepper from Vault); encrypt PII fields via pgp_sym_encrypt; upsert to DB + warm Redis. Writes batch record to cts.vault_upload_batches with upload_channel="SFTP".
  3. 3
    archive_drop_fileCopy processed file to astra-vault-archive/{bank_id}/ bucket. Remove from astra-vault-drops so it is not reprocessed. Non-fatal — if archive fails, batch is already committed; warning logged.

What Is Now Live

  • Zero CBS API dependency — UCBs that cannot expose CBS APIs can drop a CSV to MinIO. File-drop removes the single biggest onboarding blocker.
  • Both channels share VaultUploadProcessor — identical hashing, encryption, DB write, Redis warm. Only upload_channel and uploaded_by differ.
  • Single PII crypto utility — shared/utils/pii_crypto.py is the only place HMAC-SHA256 and pgp_sym_encrypt are called. All 9 files that previously had inline hmac.new() now import from here. Raises ValueError if pepper is empty — silent plain-SHA256 is impossible.
  • PPS: 5 fields exactly — account_number, cheque_number, cheque_date, amount, payee_name. expires_at is computed. registration_channel is derived from upload context. RBI compliance, no custom fields.
  • All vault DB tables scoped by bank_id — NOT NULL, first key in every index. Cross-bank row leakage is impossible at DB level.
  • Alembic chain current — latest head: 20260818_pps_vault_fix. No new migrations needed for VaultFileDropWorkflow (code-only).

Redis Key Map

All vault Redis keys across both clusters. Raw account numbers never appear as keys — all keyed by HMAC-SHA256 with bank-specific pepper.

Key PatternTypeValue / Fields
sig:{bank_id}:{hmac(bank_id:acct)}:{signatory_id} LIST Packed float32 embeddings. One item per specimen. No TTL. redis-cts.
pps:{bank_id}:{hmac(bank_id:acct)}:{cheque_number} HASH Fields: amount, payee, cheque_number. TTL = cheque validity. redis-cts.
acct:{bank_id}:{hmac(bank_id:acct)} HASH Fields: account_type, account_status, branch_ifsc, branch_manager_email, holder_name_display, last_synced_at. No TTL. redis-cts.
chq:{bank_id}:{hmac(bank_id:acct)}:{cheque_number} HASH Fields: status, issued_date, series_end. No TTL. Rebuilt daily. redis-cts.
stop:{bank_id}:{hmac(bank_id:acct)} SET Members: active cheque_numbers under stop instruction. Partial index mirror for fast set-membership check. redis-cts.
msv:{bank_id}:{account_hash}:{signatory_id} LIST Packed float32 embeddings. One item per specimen. allkeys-lru eviction. redis-msv cluster (isolated from CTS).
Pepper rotation: The HMAC pepper for each bank is rotated every 24 hours by HashiCorp Vault dynamic secrets. After rotation, VaultSyncWorkflow (or BulkVaultSeedWorkflow) must re-hash all keys and re-warm Redis. Keys written with the old pepper are deleted as part of the warm cycle — no stale keys remain after a successful sync.
