**How a cheque moves:**
```

  → scripts/local/run.py detects it

  → writes inward file to bank1-vvsb/inward_queue/
  → submits ChequeProcessingWorkflow to Temporal (task queue: cts-processing-vvsb)
  → IET watchdog spawned first (always)
  → full inward pipeline runs
  → decision written to decisions/bank1-vvsb-inward/
```

## 4. What the System Can Evaluate — Full Capability Map

### 4.1 Signature Count

| Variation | Detection | Outcome |
|---|---|---|
| No signature | `detect_signatures` → ABSENT | HUMAN_REVIEW / `NO_SIGNATURE` |
| Single signature (S-SVS path) | Detect → crop → embed → cosine vs vault | PROCEED if score ≥ threshold; HUMAN_REVIEW if below |
| Two or more signatures | sig_count ≥ 2 detected | HUMAN_REVIEW / `MULTI_SIGNATURE_DETECTED` (M-SVS is designed but routes to HR currently) |
| Signature outside designated box | `MISALIGNED` fraud flag | HUMAN_REVIEW / `SIGNATURE_FRAUD_SUSPECTED` |
| Faint ink — photocopied / printed signature | `FAINT_INK` flag | HUMAN_REVIEW |
| Smudged ink | `SMUDGED` flag | HUMAN_REVIEW |
| Signature with overwriting (ink on ink) | `OVERWRITTEN` flag | HUMAN_REVIEW |
| Different ink colours in signature zone | `MULTIPLE_INKS` flag | HUMAN_REVIEW |

Note on multi-signature: `detect_signatures.py` comment describes M-SVS (mandate BRE), but `signature.py` line 303 routes sig_count > 1 directly to HUMAN_REVIEW. MSV module exists in `modules/msv/` but is not yet wired into CTS inward. Multi-signature cheques = HUMAN_REVIEW in current production code.

### 4.2 Script and Language

| Variation | OCR Mode Required | How Handled |
|---|---|---|
| English cheque (Latin) | FULL_IMAGE (default) or PARTIAL_IMAGE | GOT-OCR2 |
| Hindi / Marathi payee name (Devanagari) | PARTIAL_IMAGE | IndicOCR → falls back to GOT-OCR2 if Latin detected or IndicOCR down |
| Gujarati payee name | PARTIAL_IMAGE | IndicOCR (same adaptive routing) |
| Mixed: English fields + Devanagari payee | PARTIAL_IMAGE | Per-zone: date/amount/MICR = GOT-OCR2 always; payee/words = IndicOCR |
| Amount in words in Hindi (एक लाख बीस हजार) | PARTIAL_IMAGE | IndicOCR → `amounts_match()` cross-checks vs figures field |

Fields **always** routed to GOT-OCR2 regardless of script (`ALWAYS_LATIN`):
- Date, Amount figures, MICR band

Fields using IndicOCR when Devanagari is detected (`SCRIPT_ADAPTIVE`):
- Payee name, Amount in words

For demo: if `ai_config["ocr.mode"]` = `FULL_IMAGE` (default), IndicOCR is not invoked. Devanagari text goes to GOT-OCR2 which handles it reasonably. To show full Indic support, set `ocr.mode = PARTIAL_IMAGE` and run IndicOCR service at `services.indic_ocr.url`.

### 4.3 Alteration Types — 6 Detection Layers

`detect_alteration` runs Qwen2-VL 72B (L2 forensic) against all 7 cheque fields:
`amount_figures`, `amount_words`, `date`, `payee_name`, `drawer_name`, `account_number`, `micr_band`

| Fraud Type | Detection Layer | Example |
|---|---|---|
| Overwritten amount (₹9,000 → ₹90,000) | Layer 1 (field content) + Layer 2 (ink physics) | Cat C cheques |
| Year tampered (2024 → 2026) | Layer 1 + Layer 4 (correction fluid spectral) | Cat D cheques |
| Payee name changed | Layer 1 + Layer 2 | Any field |
| Account number altered | Layer 1 | account_number |
| MICR line tampered | Layer 1 + Layer 3 (paper fibre distortion) | micr_band |
| Correction fluid (Tipp-Ex / Whiteout) | Layer 4 — luminance spike, sharp boundary | Cat C/D |
| Chemical erasure (ink eradicator) | Layer 5 — solvent halo, colour shift | Any field |
| Overwriting brightness anomaly | Layer 6 — luminance under overwritten strokes | Any field |
| Mechanical erasure (rubber / blade) | Layer 3 — raised fibres at ≥200 DPI greyscale | Any field |

Layer 3 (paper fibre) is most effective at 200+ DPI greyscale scan. Phone photos will not show fibre distortion. For demo: scan at 300 DPI or use the synthetic PIL images (which have visible Tipp-Ex rectangles — Layer 4 detects these well).

### 4.4 CTS-2010 Security Features — 4 Mandatory Checks

`check_security_features` runs Qwen2-VL against 4 mandatory features:

| Feature | Description | If Missing |
|---|---|---|
| `void_pantograph` | Latent anti-photocopy "VOID" background pattern | HUMAN_REVIEW |
| `rupee_symbol` | ₹ security watermark or print | HUMAN_REVIEW |
| `micro_lettering` | Fine repeating "CTS" or bank name text | HUMAN_REVIEW |
| `printer_name_cts2010` | "CTS-2010" or NPCI-approved printer name on cheque | HUMAN_REVIEW |

**Current demo images:** `generate_images.py` prints "CTS 2010" as a header badge but does NOT render void pantograph background, ₹ watermark, or micro lettering. Security features check will return HUMAN_REVIEW for all current demo cheques unless the generator is updated. DEGRADED (model down) continues without blocking — but HUMAN_REVIEW (features missing) does route to human review.

**Action required:** Update `generate_images.py` to add void pantograph dot-lattice background, ₹ symbol watermark, and micro lettering strip.

### 4.5 Amount Cross-Check (OCR internal)

| Scenario | Detection | Outcome |
|---|---|---|
| Figures match words (₹1,20,000 = "One Lakh Twenty Thousand") | `amounts_match()` → True | PROCEED |
| Figures ≠ words (₹35,000 vs "Twenty Five Thousand") | `amounts_match()` → False | HUMAN_REVIEW / `amount_figures_words_mismatch` |
| SMB instrument (MICR prefix matches routing table) | `MICRPrefixRouter` | tags as `SUB_MEMBER`, sets `sub_member_id` |

### 4.6 PPS (Positive Pay System) — 5-Flag NPCI Decision Tree

| Flag | Meaning | Outcome |
|---|---|---|
| P — Positive match | Registered; amount and payee match within ₹1 | PROCEED |
| D — Duplicate | Same cheque number presented before | AUTO_RETURN (code 41, not customer fault) |
| Y — Financial mismatch | Registered but amount or payee diverges | HUMAN_REVIEW |
| Z — No data in vault | PPS registered by issuer but no vault entry | HUMAN_REVIEW if amount ≥ `pps_mandatory_threshold`; PROCEED if below |
| N — Not registered | Customer opted out of PPS | PROCEED |
| Vault miss (no entry at all) | Same routing as flag Z | Threshold check |

### 4.7 CBS Checks

| CBS Result | Outcome |
|---|---|
| Balance sufficient + account ACTIVE | PROCEED |
| Insufficient funds | RETURN (auto, URRBCH code 01) |
| Account FROZEN | AUTO_RETURN (code 55) |
| Account DORMANT | HUMAN_REVIEW |
| Account CLOSED | AUTO_RETURN (code 50) |
| CBS unreachable | Graceful degrade — continues; higher human review rate |

### 4.8 Stop Payment

| Status | Outcome |
|---|---|
| Active stop payment on this cheque number / account | AUTO_RETURN (URRBCH code 20) |
| No stop payment | PROCEED |
| CBS unreachable | Graceful degrade — assumes no stop payment, continues |

### 4.9 Final Decision Priority Order (inward)

```
Priority 0: Kill switch active (KP or KC)     → HUMAN_REVIEW  [RBI mandate, supersedes all]
Priority 1: CBS returned RETURN status         → STP_RETURN
Priority 2: Alteration detected               → STP_RETURN
Priority 3: Fraud score > auto_return_threshold → HUMAN_REVIEW
Priority 4: OCR confidence < threshold        → HUMAN_REVIEW
Priority 5: Signature score < threshold       → HUMAN_REVIEW
Priority 6: CBS unavailable                   → HUMAN_REVIEW
Priority 7: PPS miss / mismatch               → HUMAN_REVIEW
Priority 8: CBS escalation                    → HUMAN_REVIEW
Priority 9: All clean + fraud below STP threshold → STP_CONFIRM
Else:                                          → HUMAN_REVIEW
```

## 5. Vault Population — What, When, How

### 5.1 Signature Vault

**What it stores:** 512-dimensional float32 embedding vectors for each registered signature specimen per account.

**Redis key format:** `sig:{bank_id}:{hmac_sha256(bank_id:account_number)}`

**What must exist before clearing runs (per drawee account):**
- 1 to 3 signature specimen images (scanned signed documents from account opening)
- Each image embedded via Siamese model → 512-dim vector stored in Redis + YugabyteDB

**How it is populated in production:**
`VaultSyncWorkflow` runs at 6AM daily. Pulls specimen images from CBS (`get_signature_specimens()`), embeds them, writes to Redis + YugabyteDB.

**How it is populated for demo:**
`scripts/local/seed_vault.py`:
- Reads `demo/seed/signatures/{customer_id}.png` for each drawee account
- Runs through embedding model → 512-dim vector
- Writes to Redis and YugabyteDB using the same key format as production
- For Cat I (signature mismatch): loads `{customer_id}_on_cheque.png` as the vault entry so the specimen deliberately does NOT match what is on the cheque

**Fast path without GPU:**
`generate_images.py` uses a deterministic sinusoidal algorithm (seeded from customer_id) for all signatures. The same algorithm generates both the cheque signature and the specimen. Pre-compute embeddings offline from these images using any CPU-mode model (lightweight ResNet) — cosine similarity between same-algorithm outputs will be high by construction. For Cat I, a different frequency + ink colour is used — cosine similarity will be low by construction.

**Success threshold:** cosine similarity ≥ `ai_config["ai.signature.min_match_score"]` (default 0.85 from config).

### 5.2 PPS Vault

**What it stores:** Pre-registered cheque details per account.

**Record format:**
```json
{
  "account_number": "20010010900010",
  "cheque_number": "100000",
  "amount": 120000.00,
  "payee": "M/s Sunrise Trading Co.",
  "npci_flag": "N"
}
```

**For demo:**
- All straightforward cheques: `npci_flag: "N"` (customer opted out) → PROCEED always
- CHQ-SRCB-C009 (PPS mismatch demo): `npci_flag: "P"`, registered amount `500000`, presented amount `750000` → HUMAN_REVIEW
- `scripts/local/seed_pps.py` writes these from `demo/seed/pps_records.json`

## 6. Infrastructure Required to Run the Demo

### 6.1 What to Start

```bash
temporal server start-dev        # localhost:7233 — single binary
redis-server                     # localhost:6379
immudb                           # localhost:3322 — single Go binary, 30 MB
```

**Why Immudb must be real:** `write_audit` has `AUDIT_RETRY = unlimited`. If Immudb is None and we add a None-guard, we lose the immutable audit trail story — which is a core differentiator for banks. Run real Immudb. It boots in 2 seconds.

### 6.2 Environment Variables

```bash
export ASTRA_HF_BASE_URL="https://your-endpoint.hf.space/v1"
export ASTRA_HF_API_KEY="hf_xxxxx"
export ASTRA_TEMPORAL_ADDRESS="localhost:7233"
export ASTRA_REDIS_URL="redis://localhost:6379"
export ASTRA_IMMUDB_ADDRESS="localhost:3322"
```

### 6.3 Config Layer — `LocalConfigService`

NOT `DemoConfigService`. The name matters — it's a **local deployment config** not a demo bypass.
Banks deploying ASTRA before their Vault is provisioned use exactly this.

- `temporal.address` → `$ASTRA_TEMPORAL_ADDRESS`
- `vllm.l1_url` → `$ASTRA_HF_BASE_URL` (HuggingFace, same OpenAI-compatible API as on-prem vLLM)
- `vllm.l2_url` → `$ASTRA_HF_BASE_URL`
- `redis.cts.url` → `$ASTRA_REDIS_URL`
- `immudb.address` → `$ASTRA_IMMUDB_ADDRESS`
- All secrets (Vault paths) → raise `ConfigKeyNotFoundError` → deps degrade gracefully

This is valid production behavior for a bank in pre-Vault provisioning phase.

## 7. What Needs to Be Fixed in Production Code

### 7.1 Hard Blocker 1 — `ngch_filer.py` line 53

**Problem:** `await ngch_adapter.file_decision(...)` — if `ngch_adapter` is None → AttributeError → Temporal retries 3x → workflow FAILS. Every inward cheque fails at finalise.

**Fix (production code, not a stub):**
```python
if ngch_adapter is None:
    log.warning("ngch_filer.adapter_unavailable", instrument_id=inp.instrument_id)
    return NGCHFilingResult(
        ack_id=f"NGCH-QUEUED-{inp.instrument_id[:8]}",
        status="QUEUED_FOR_RETRY",
    )
```
This is valid production behaviour — NGCH could be temporarily unreachable. Temporal will retry the workflow when adapter becomes available.

### 7.2 Hard Blocker 2 — `write_audit.py`

**Problem:** `AUDIT_RETRY = unlimited retries`. `write_audit` re-raises all failures. If Immudb is None or unreachable → workflow hangs forever.

**Fix:** Run real Immudb (30 MB binary). No code change needed once Immudb is running. This is the correct fix.

Alternatively, add a `max_attempts=20` to `AUDIT_RETRY` as a safety backstop — after 20 attempts (10+ minutes), fail the activity with a clear error rather than hanging silently forever.

### 7.3 Hard Blocker 3 — No folder → Temporal trigger

**Problem:** Nothing watches a drop folder and submits `OutwardScanWorkflow` without Kafka.

**Fix:** `scripts/local/run.py` — an asyncio folder watcher that:
1. Detects new `.png` file in `demo/bank2-srcb/scanner_drop/`
2. Reads paired `.json` sidecar (or looks up `demo/seed/cheques.json`)
3. Submits `OutwardScanWorkflow` to Temporal for SRCB
4. Polls Temporal for workflow completion
5. If ACCEPTED: writes NGCH presentment file → routes to VVSB inward queue → submits `ChequeProcessingWorkflow`

This is the production SMB scanner trigger — just folder-based instead of Kafka. The production `OutwardScanTrigger` does the same thing from a Kafka consumer.

### 7.4 Medium Blocker 4 — Security features always HUMAN_REVIEW

**Problem:** `generate_images.py` renders "CTS 2010" as a text badge but does NOT render:
- Void pantograph (dot-lattice anti-photocopy background)
- ₹ symbol watermark
- Micro lettering ("CTS" repeated in fine text)

All demo cheques fail `check_security_features` → HUMAN_REVIEW.

**Fix:** Update `generate_images.py`:
- Add fine dot-lattice background (void pantograph simulation) using PIL `ImageFilter` or point grid
- Add semi-transparent ₹ watermark centered on cheque body
- Add micro text strip at bottom margin

### 7.5 Worker Dependency Injection

**Fix:** Add `override_deps: dict | None = None` to `build_bound_activities()` and `run_worker()`.
This lets `scripts/local/run.py` pass in `LocalCBSConnector`, `LocalNGCHAdapter` etc. without touching any workflow or activity code.
