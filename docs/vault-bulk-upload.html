How bulk upload fits the normal sync flow
Normal operation: All vaults are populated automatically each day by VaultSyncWorkflow pulling from the CBS connector (6 AM). Bulk upload is for initial seeding (go-live), CBS connector unavailability (disaster recovery), or corrections that cannot wait for the next sync cycle.
Vault miss rule is non-negotiable: Any record missing from any vault at clearing time routes to HUMAN_REVIEW — never AUTO_RETURN. Bulk upload does not change this routing policy. Incomplete uploads increase the human review queue; they do not cause incorrect returns.
PPS Vault — Positive Pay System
Pre-registers individual cheque leaves issued by the drawee bank. Each registration covers one specific cheque leaf — one account, one cheque number, one date, one amount, one payee. At clearing, the incoming cheque is matched against this vault; a miss routes the instrument to human review.
Template filename
pps_upload.csv
Min. role ops_manager
bank_id is never a CSV column. Every row is automatically scoped to the authenticated user's bank (for UI uploads, from the session JWT; for SFTP file-drop, from the MinIO path astra-vault-drops/{bank_id}/pps/). Do not add a bank_id column — the system will reject files that include it.
Field specification — RBI Positive Pay (5 mandatory fields)
Column Type Required Description Example
account_number string ✓ Yes Full account number of the drawer. HMAC-SHA256-hashed on ingest (bank-specific pepper from Vault) — never stored raw. Used as the vault lookup key. 00112233445566
cheque_number string ✓ Yes The specific 6-digit cheque leaf serial number, zero-padded. One registration per leaf — not a range. Together with account_number, forms the composite vault key. 000123
cheque_date date ✓ Yes Date printed on the face of the cheque. Format: YYYY-MM-DD. The system computes expiry as cheque_date + 90 days automatically — do not supply an expiry column. 2026-08-10
amount decimal ✓ Yes Cheque amount in INR, two decimal places. No commas, no currency symbols. Stored as range bucket internally; exact amount is never persisted. 750000.00
payee_name string ✓ Yes Payee name as registered with the bank — must match what appears on the cheque face. UTF-8 encoding; Indic scripts accepted. Stored as SHA-256 hash; the raw name is never persisted. Reliance Industries Ltd
No series ranges. PPS is per-leaf — one row per cheque number. If a customer pre-registers 10 cheques from the same book, that is 10 rows in this file. The Cheque Leaf Vault (separate tab) handles book-level range uploads.

One row = one cheque leaf. expires_at is computed automatically as cheque_date + 90 days — never include it in the CSV. DEACTIVATE: only account_number and cheque_number are required; other columns are ignored. The previous registration is snapshotted to history before deactivation.

Account Vault
Two-file upload: Summary carries one operational record per account (branch contacts, type, status); Detail carries one row per holder per account (holder identity and role). ASTRA derives the masked display string from Detail rows — the bank never constructs it directly. Covers all account structures: individual, joint, corporate, HUF, partnership, and trust.
bank_id is never a CSV column. Every row is automatically scoped to the authenticated user's bank (for UI uploads, from the session JWT; for SFTP file-drop, from the MinIO path astra-vault-drops/{bank_id}/account_detail/). Do not add a bank_id column — the system will reject files that include it.
Upload order: Summary must be uploaded first. Detail rows referencing an account_number not present in Summary are rejected. Both files are processed atomically within their own upload — a row error rolls back that file only.

Cheque Leaf Vault
Tracks the status of every issued cheque leaf. A bloom filter of cancelled serials is checked before the AI pipeline — preventing GPU time spent on obviously invalid instruments. Bulk upload is how the bank seeds the vault at go-live from CBS issuance records.
Template filename
cheque_leaf_upload.csv
Min. role bank_it_admin
bank_id is never a CSV column. Every row is automatically scoped to the authenticated user's bank (for UI uploads, from the session JWT; for SFTP file-drop, from the MinIO path astra-vault-drops/{bank_id}/cheque_book/ or astra-vault-drops/{bank_id}/leaf_status/). Do not add a bank_id column — the system will reject files that include it.
Field specification
Column Type Required Description Example
account_number string ✓ Yes Account number to which this cheque book was issued. 00112233445566
cheque_number_from string ✓ Yes First leaf number in the issued cheque book (zero-padded, 6 digits). 000001
cheque_number_to string ✓ Yes Last leaf number in the issued cheque book. Equal to cheque_number_from for a single-leaf upload. 000050
status enum ✓ Yes One of: ACTIVE · LOST · STOLEN · CANCELLED · USED ACTIVE
issued_date date ✓ Yes Date the cheque book was issued to the account holder. Format: YYYY-MM-DD. 2026-08-01
Range expansion: When cheque_number_from ≠ cheque_number_to, the upload processor expands each row into individual leaf entries automatically. A book of 50 leaves is one CSV row, not 50.
Sample CSV
action,account_number,cheque_number_from,cheque_number_to,status,issued_date INSERT_ONLY,00112233445566,000001,000050,ACTIVE,2026-08-01 INSERT_ONLY,00998877665544,000100,000150,ACTIVE,2026-07-15 UPDATE_ONLY,00556677889900,000205,000205,CANCELLED, UPDATE_ONLY,00334455667788,000300,000300,LOST,
Range uploads (INSERT_ONLY) auto-expand each leaf to ACTIVE. Status corrections (UPDATE_ONLY) target individual leaves — CANCELLED and LOST/STOLEN are immediately added to the bloom filter and previous status written to history.

Embeddings are computed by ASTRA — never upload vectors directly. The processing pipeline runs in the background after ZIP upload; vault entries appear in Redis within the next VaultSyncWorkflow cycle or within 30 minutes if triggered manually.
The action column — universal across all vault upload files
Every vault upload file has an action column as its first column. It is optional — if omitted from the header entirely, the system defaults all rows to UPSERT. When present, each row declares individually what should happen. This is how the same file format handles initial seeding, periodic updates, and removals without separate upload flows.
action value What it does Fails if… Typical use
UPSERT Default. Creates the record if it does not exist; updates the matched record if it does. Only non-blank columns are written — blank = leave the existing value as-is. Never fails on existence. May fail on validation (bad enum, missing required field on first insert). Day-to-day incremental sync, periodic refresh batches.
INSERT_ONLY Creates a new record. All required columns must be present. Blank optional columns use system defaults. Record already exists in the vault — the row is rejected and logged. The rest of the file continues. Go-live seeding where you want confirmation that you are not accidentally overwriting existing data.
UPDATE_ONLY Updates an existing record. Blank columns = leave as-is (partial update). To explicitly clear a field, write ~CLEAR~ as the value. Record not found in the vault — the row is rejected and logged. Prevents silent creates when intent is to update. Branch contact refresh, account status changes, holder detail corrections.
DEACTIVATE Soft-marks the record as inactive. The record is retained for audit trail — never physically deleted. Only the key columns are needed; data columns are ignored. Record not found — logged as a warning, not an error. Remove a joint holder, revoke a stop cheque instruction, expire a PPS entry, cancel a cheque book.
History table — mandatory snapshot before every change
Before any UPDATE_ONLY, UPSERT (on an existing record), or DEACTIVATE row is applied, the system snapshots the current record into a companion *_history table. This happens inside the same database transaction — either both the snapshot and the update succeed, or neither does.

Each history row captures: all column values at that moment · changed_at timestamp · changed_by (user ID of the uploader) · upload_batch_id (links back to the Immudb audit entry) · change_action (UPDATE / DEACTIVATE) · change_reason (optional free-text, bank can populate via the UI; blank on automated CBS sync).

This gives you a full queryable answer to: "What was this account's branch email on 15 August?" or "When was this joint holder removed and who authorised it?" The history table is append-only and follows the same 10-year retention as the main table.
Uniqueness rules
Within a file: The same composite key (e.g. account_number for Summary, account_number + holder_seq for Detail) may not appear twice in one upload file — even with different action values. Two instructions for the same record in one batch are contradictory and the entire file is rejected.

Across uploads: No restriction. The same account can be INSERT_ONLY'd on day 1, UPDATE_ONLY'd on day 60, and DEACTIVATE'd when the account closes — in separate upload files.
Partial update behaviour
On UPSERT (updating an existing record) and UPDATE_ONLY: blank columns are skipped — the existing vault value is unchanged. This means a branch contact refresh batch only needs account_number + the contact columns; it does not need to re-supply account_type, account_status, or any holder detail.

To explicitly clear a field (set it to empty), write the sentinel value ~CLEAR~. Example: setting branch_manager_email to ~CLEAR~ removes the stored email address.

General upload rules
Encoding
Files must be UTF-8 encoded. BOM is stripped automatically. Do not save as Windows-1252 / ANSI — Indic characters will corrupt.
Header row
Row 1 must be the header with exact column names as specified. Column order does not matter — the system maps by name, not position. The action column may be omitted entirely (defaults all rows to UPSERT).
Row limit per upload
Max 50,000 rows per file. Larger datasets must be split. Each file is processed atomically — a row-level error rolls back only that row (except within-file duplicate key, which rejects the whole file).
Date format
All dates must be YYYY-MM-DD. Indian DD/MM/YYYY and US MM/DD/YYYY formats are rejected with a validation error on that row.
Vault effect timing
PPS, Stop Cheque, and Account Vault entries are available in Redis within 30 seconds. Signature embeddings take up to 30 minutes (GPU embedding job).
Audit trail
Every upload is written to Immudb with the uploader's ID, timestamp, row count, action breakdown, and file checksum. Cannot be deleted.
PII in CSV files
Files contain full account numbers — treat as confidential. Deleted from the upload buffer after processing. Do not store in shared drives or email.
Stop Cheque — DEACTIVATE = Revoke
For the Stop Cheque file only, DEACTIVATE means "revoke the stop instruction" — the cheque is then permitted to proceed through clearing on next presentation.
Validation errors
After upload, the system returns: total rows, rows accepted, rows rejected, and a downloadable error log. Each error row includes the line number, column, value, and rejection reason. Fix only the rejected rows and re-upload — accepted rows are already committed and should not be re-submitted.
